Engineering background & proposed method

Method & Architecture

The system is a layered, registry-driven pipeline: every supported question is defined once, in one place, and the user interface, code generator, validator, and execution pipeline all derive their behavior from that single definition.

The approach

A user selects one of the supported clinical questions (or types a natural-language question that is routed to one). The system then generates a short, readable Python snippet that calls a known data-preparation function with the user's parameters; executes that snippet; validates the result against structural rules (is it a DataFrame? does it have the expected columns? is it non-empty?) plus a per-question clinical rule (for example, "all rows must be flagged abnormal"); and, only if execution or validation fails, applies a small rule-based correction and retries, up to a bounded number of attempts. The final result, the generated code, the validation message, and the full correction history are all shown to the user.

Trusted default: the 12-question registry

The constrained pipeline above is the default execution path. It never calls an external model, is fully deterministic and reproducible, and applies question-specific clinical validation rules. All 12 supported question types run through it.

Optional & experimental: "Advanced: AI writes code"

An explicitly opt-in, off-by-default mode invokes a large language model (LLM) "programmer agent" that writes a pandas snippet for a free-form question. That snippet never runs directly: it is checked against an abstract-syntax-tree (AST) allow-list and executed inside a restricted sandbox, following the same generate → execute → validate → retry pipeline before anything is shown to the user.

Architecture — single-responsibility modules around one registry

Single source of truth

The question registry (questions.py) is the central configuration layer. The UI, code generation, validation, and execution pipeline all derive their behavior from the same registry definition — so adding a question is a one-place change, and the components cannot drift out of sync.

Extending the registry: adding a question really is a one-place change

  1. Add a data-preparation function in data_prep.py that returns a DataFrame.
  2. Add a QuestionSpec entry to QUESTION_REGISTRY in questions.py — id, label, parameters, data function, expected columns, and an optional validator and chart spec.
  3. If the question needs a new input type, add an entry to PARAM_DEFS.

No changes to app.py, code_generation.py, validation.py, or main_pipeline.py are required — they all read from the registry.

Algorithms

Code generation

generate_code(spec, params) reads the target data function's own signature with Python's inspect module, so it needs no per-question hard-coded argument list. It builds a call such as result = get_latest_lab_value(199884, 50902) directly from the QuestionSpec and the supplied parameters.

Execution

For the registry path, execute_generated_code runs the snippet with Python's exec() against a namespace built only from the registry's known functions — never against arbitrary user code — inside a try/except that captures success, the result object, and any error message and status.

Validation

validate_result first verifies that execution completed and returned a result. For tabular results it verifies the value is a pandas DataFrame containing all of the question's expected columns and rejects an empty DataFrame (which the UI reports separately as a neutral "no matching records" state). Finally it applies the question-specific rule, where one exists — for example: abnormal-result questions must return only FLAG = abnormal rows; "latest value" and summary questions must return exactly one row; trend and date-range questions must be sorted by time ascending; and the dataset-wide aggregate must satisfy Abnormal + Normal = Total Tests for every admission.

Correction

run_with_correction executes and validates the code and, on failure, rewrites a small, explicit map of known function-name typos — matched on whole identifiers only, via regex word boundaries, so a wrong name that happens to be a prefix of a valid one is never corrupted — and retries, up to 2 attempts. Every attempt's code, execution outcome, and validation outcome is recorded and shown in the UI's Correction Attempts tab.

Natural-language routing (controlled NLP)

The NLP part is used in the optional natural-language question box. It is not an open medical chatbot, and it does not answer directly from the dataset. Its role is to translate a human sentence into one of the 12 approved question templates plus validated parameters.

The default router in question_router.py first uses deterministic NLP rules: it normalizes the text, detects the intent from clinical words such as abnormal, latest, trend, count, patient, admission, and date range, extracts parameters such as HADM_ID, patient id, dates, and lab-test names, maps lab names to known ITEMID values, and checks the result against QUESTION_REGISTRY.

If the rule-based router cannot safely match the sentence and an API key is configured, llm_router.py can use an LLM fallback. The model is only allowed to return structured JSON with a supported question id and parameters. That output is parsed and validated before the normal generate → execute → validate → correct pipeline runs. In the normal NLP route, the LLM never writes code and never queries the data directly.

Sandboxed LLM code generation (optional path)

check_code() parses a candidate snippet with Python's ast module and rejects it unless every node type is on an explicit allow-list: imports, loops, function and class definitions, private or dunder attribute access, dangerous builtins, and file-, network-, or evaluation-related methods (to_csv, read_sql, eval, query, …) are all rejected. Accepted code runs in a worker thread inside a restricted namespace containing only pd, a read-only df, and a small set of safe builtins — under a soft timeout and an output row cap — and the result must still pass a deterministic validation gate. On failure, the error feedback is returned to the LLM for another bounded attempt.

Data: inputs and preprocessing

The system is built on three source tables of MIMIC-III (Medical Information Mart for Intensive Care): ADMISSIONS (one row per hospital admission), LABEVENTS (one row per laboratory measurement), and D_LABITEMS (a lookup table mapping ITEMID values to human-readable laboratory test names).

An initial schema-inspection pass (Google Colab, pandas) quantified missing values in every field the supported questions rely on — notably 371,649 LABEVENTS rows with no HADM_ID (which cannot be attributed to an admission) and 994,847 rows with an empty FLAG (expected: normal results are simply left unflagged rather than explicitly marked "normal"). The cleaning pipeline then:

  1. keeps only the columns the project needs,
  2. removes LABEVENTS rows with a null HADM_ID,
  3. joins LABEVENTS to ADMISSIONS on HADM_ID, and
  4. attaches a readable lab name from D_LABITEMS via ITEMID.

The 12 supported questions

How the question set was selected

The 12 questions were not chosen randomly, and the LLM was not used as the authority for deciding the medical scope. The set was selected from the project requirements, the team's Part 1 data-analysis work, and the actual structure of the MIMIC-III laboratory dataset.

Because the project did not have a real doctor or researcher as a direct client, we treated the target users as two expected profiles: a Doctor who needs fast admission-level review, and a Researcher who needs repeatable, exportable analysis. That is why the questions cover both bedside-style review (abnormal results, latest value, trends, all tests, first-vs-last comparison) and research-style analysis (summary statistics, abnormal/normal counts, date ranges, patient admissions, and a dataset-wide aggregate).

LLM assistance was used only as support for brainstorming, wording, and optional natural-language routing. The final question set was accepted only when each question could be answered from the available columns, matched the project goal, served one of the two user profiles, and could be validated with deterministic rules.

Tools & technologies

  • Python 3.10+ (developed and tested on Python 3.13), with pandas for data loading, preprocessing, and analysis.
  • Streamlit for the interactive web-based user interface, with an explicitly pinned dark theme (.streamlit/config.toml) so the app renders identically regardless of the viewer's OS or browser theme.
  • pytest + pytest-cov for automated testing, with an 85% minimum coverage gate enforced in pyproject.toml (final coverage: 94%).
  • Optional LLM providers — Anthropic, OpenAI, or Google Gemini — selected by the available API key and accessed through a lightweight httpx-based client with automatic retries and a mock/none fallback. The system is fully functional with no key at all.
  • uv for dependency management (pyproject.toml / uv.lock).
  • Dataset: the MIMIC-III clinical database (ADMISSIONS, LABEVENTS, D_LABITEMS), cleaned and merged into a single working CSV.

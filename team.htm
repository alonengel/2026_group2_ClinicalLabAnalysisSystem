Who we are & how we worked

Team & Process

The four of us built the Clinical Lab Analysis System for the seminar Software Engineering in the Age of AI at the University of Haifa. This page covers who did what, how the project evolved, the difficulties we ran into, and what we learned from them.

The team

We worked as two sub-teams around a shared core, mirroring the system's own split between data and pipeline:

Hala Hillou & Dana Nmarny

Questions & data sub-team

Defined and refined the clinical question set, prepared and cleaned the MIMIC-III (Medical Information Mart for Intensive Care) dataset, and built the question-selection and data-preparation components.

Anas Khoury & Alon Engel

Pipeline, UI & tests sub-team

Built code generation, execution, validation, the correction loop, and result presentation; led the registry refactor; and implemented the natural-language router, the Streamlit UI, and the test suite.

Test cases, integration, and evaluation were shared work across all four team members.

Development phases

  1. Scope and data Froze the MVP scope (a small predefined question set; ADMISSIONS + LABEVENTS + optional D_LABITEMS; lab rows restricted to a valid admission ID), chose the first 5 question types, inspected the raw MIMIC-III schema in Google Colab, and built the cleaned, filtered, merged working dataset.
  2. First MVP Defined the 5-module architecture (question selection, data preparation, code generation, validation & correction, result presentation), picked the Python + pandas + Streamlit stack, and implemented each module — first against mock DataFrames to validate the interfaces, then wired to the real dataset — reaching a working end-to-end console pipeline before building the Streamlit UI.
  3. Registry refactor and polish Replaced the 5 hard-coded questions with a single config-driven QUESTION_REGISTRY that every other module reads from, added 6 further question types, and polished the UI — category filter, dynamic per-question parameter widgets, trend chart, status banner, and a pinned dark theme.
  4. Final deliverables and extensions Wrote the report, slide deck, and demo script; added the 12th, dataset-wide aggregate question; added controlled natural-language routing, later with an optional large-language-model (LLM) fallback; added the experimental sandboxed "Advanced: AI writes code" agent loop inspired by AgentCoder and Self-Edit; and added the role-based Doctor / Researcher workspace UI.

Challenges and how we solved them

The cleaned dataset was too large for git

cleaned_merged_dataset.csv (~130 MB) exceeds GitHub's 100 MB per-file limit, and Git LFS was judged not worth its quota and setup overhead for a course project. Resolution: the dataset is kept out of version control and the app downloads it automatically on first run from a shared location, with a documented manual fallback.

A naive typo-correction rule corrupted a valid function name

The first version of the rule-based corrector used plain substring replacement, so the fix for the typo get_abnormal_result silently rewrote the valid, longer identifier get_abnormal_results_for_lab — which contains that substring — into something else. Resolution: the corrector now matches whole identifiers only, using regex word boundaries, and a regression test pins this behavior.

Theme inconsistency made the UI unreadable for some users

Headers and cards were unreadable when a viewer's system theme did not match the app's assumptions. Resolution: the Streamlit theme was pinned explicitly in .streamlit/config.toml, so the app renders identically regardless of the viewer's OS or browser theme.

How much autonomy to give generated code

The initial scope decision excluded any LLM code generation from the MVP, since free-text questions would break the validator's assumption of known expected columns and could execute arbitrary code. The decision was later revisited — but only by adding a second, clearly optional and off-by-default path, gated by a purpose-built sandbox (an abstract-syntax-tree allow-list, restricted builtins, a worker-thread timeout, and a row cap) that was built and tested before any LLM-authored code was allowed to run at all, rather than by relaxing the guarantees of the trusted registry path.

Keeping a growing question set consistent across modules

As the question count grew from 5 toward 12, keeping the UI, code generator, validator, and pipeline in sync by hand became error-prone. Resolution: the registry refactor introduced questions.py as the single source of truth. Every component derives its behavior from the registry, so adding a new question now requires updating only one central definition.

Choosing the 12 questions without a real clinical client

The project had no doctor or researcher acting as a direct client, so no one could simply hand us the question list. Resolution: we grounded the scope in research — how Israeli health-fund portals present lab results (parts of Maccabi's Health Guide, Clalit's Your Health portal), the team's Part 1 data-analysis work, and iterative brainstorming sessions with an LLM (Claude) — then modeled two user profiles (Doctor: narrow, admission-specific answers; Researcher: patterns across the data) and accepted a question only if it met four engineering criteria: answerable from the dataset columns, matching the project goal, meaningful for one of the two profiles, and validatable with deterministic rules. The full rationale is on the Method page.

Proving the test suite is sufficient, not just large

A count like 170 tests says nothing by itself. Resolution: the suite was built risk-first and argued in terms of three kinds of coverage — code coverage (94% of lines, 85% gate enforced), bug & failure coverage (negative tests for every error path, plus regression tests that pin previously fixed bugs), and flow coverage (end-to-end tests driving both role workspaces through all 12 questions). The breakdown is on the Results page.

Demonstrating self-correction when the generator never fails

The registry-driven generator never produces a typo on its own — which made the correction loop impossible to show in a live demo. Resolution: a "Demo: inject a typo" checkbox (available for questions 1–5) deliberately corrupts the generated function name, so any examiner can watch the loop detect the failure, repair the name, and re-run. The before/after is captured in the demo gallery.

No room for market validation or a clinician-tested proof of concept

Within the size and time limits of a one-semester university seminar, there was no realistic way to run market validation or put the proof of concept in front of practicing clinicians — no real users, no external baseline system, and no time for a formal user study. Resolution: we treated this as an explicit scope limitation rather than papering over it. User needs were approximated through portal research and the two role profiles, the evaluation relied on internal baselines that ablate each guardrail (see Results), and the report's limitations section states the gap openly — with a clinician/researcher user study proposed in future work.

Why the course website was not built in Google Sites

The first reason is the honest one: Google Sites is visually basic. Its templates are plain, customization is shallow, and it has no building blocks for the components this site relies on — the clinical design theme, stat tiles, coverage bars, the SVG pipeline diagram, styled tables, and the captioned screenshot gallery. The assignment explicitly grades aesthetics and uniformity, and our review of 39 past course sites showed Google Sites teams usually ending with the same generic default template. Standalone HTML/CSS was the only way to build a site that looks designed rather than assembled.

Self-contained files remove permission risk. Google Sites submissions often rely on Google Drive links, and several past sites had files behind permission walls or dead links. Our site keeps every PDF and PPTX inside the submitted folder with relative links, so it works offline from the unzipped folder with nothing external to break.

The submission is more durable. The zip is graded exactly as built. Google Sites requires ownership transfer and can later become private or login-walled, as happened to the 2019 team's Google Site. A standalone zip cannot lose permissions, disappear behind account access, or change after submission.

The precedent is accepted. Strong previous course submissions, including the 2024 cognitive-bias site and the 2023 Speedsters site, used standalone delivery. Course staff also republish standalone zips on GitHub Pages, so this is a normal accepted path.

It fits the software-engineering seminar. The site lives in Git, and automated checks verify internal links, relative links, image alt text, and packaging rules. package.py reproducibly builds the required zip format. Google Sites would make most of that manual clicking instead of an engineered, tested workflow.

Trade-off: Google Sites gives free hosting and easy WYSIWYG collaboration. We covered those needs with GitHub for collaboration and a standalone site that needs no hosting at all.

Lessons learned

  • A single source of truth is worth the refactor. The question registry removed an entire class of drift bugs between the UI, the generator, and the validator — and made every later addition (questions 6–12, the role-based UI, the code-generation agent) a localized change.
  • Deterministic validation plus a bounded correction loop is a cheap, high-value safety net. It turns silent or malformed output into an explicit, auditable status without needing a model call for the common failure modes.
  • Sandboxing has to come before capability. The AST allow-list, restricted builtins, timeout, and row cap were designed and tested before any LLM-authored code was allowed to execute — not retrofitted afterward.
  • Lightweight, in-repository orchestration beat heavier frameworks. Skipping CrewAI / AutoGen / LangGraph kept the experimental code-generation loop easy to debug and appropriate for the project's scope — consistent with AgentCoder's own finding that clearly separated responsibilities matter more than orchestration machinery.

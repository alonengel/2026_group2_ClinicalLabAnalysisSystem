Evaluation procedure

The system was evaluated in five complementary steps: (1) manual verification of every question type on multiple admissions and patients against the source data; (2) an automated suite of 170 unit and integration tests; (3) end-to-end tests driving the real UI through all 12 questions in both role workspaces; (4) negative and edge-case testing of every failure path; and (5) internal baseline comparisons that ablate each guardrail. Key findings: all 12 question types pass both manual and automated checks, every injected failure becomes an explicit outcome or an automatic repair rather than a silent error, and each guardrail demonstrably catches failures that would otherwise pass unnoticed — the sections below report each step in detail.

Why 170 tests

The suite follows a risk-based approach rather than chasing a number: every core responsibility has at least one direct test, the highest-risk paths (validation failures, sandbox rejection, routing decisions, no-record states) have both positive and negative tests, and end-to-end tests drive both role workspaces through all 12 questions. Taken together, that gives three kinds of coverage: code coverage (94% of lines, 85% gate enforced), bug & failure coverage (negative tests for every error path, plus regression tests that pin previously fixed bugs, such as the typo-corrector regression), and flow coverage (end-to-end tests from input widgets to rendered results). Because the suite is deterministic and mostly offline, the same checks run identically after every change, without depending on a live LLM response. The full per-test breakdown is in the test report (PDF).

Edge cases exercised

  • No-records path: a question with no matching data shows a neutral "no matching records" state rather than an error.
  • Correction loop: a deliberately misspelled function name is auto-corrected and re-run (used as a live demo, since the real generator never emits a typo on its own).
  • Regression guard: the typo corrector no longer corrupts the valid name get_abnormal_results_for_lab, which contains a shorter valid identifier as a substring.
  • Validation failures: execution errors, a None result, a non-DataFrame result, missing columns, an empty frame, and a failing per-question rule are all handled and reported distinctly.
  • Dataset-wide aggregate (Q12): per-admission counts are cross-checked against the single-admission view (Q7), and Abnormal + Normal = Total Tests is validated for every row.
  • Code-generation sandbox: imports, open, dunder/underscore attributes, file/network/eval methods, loops, and syntax errors are all rejected by the abstract-syntax-tree (AST) allow-list; runtime errors, timeouts, and row caps are exercised with a fake large language model (LLM) that is made to fail, be blocked, and refine.

Comparison to baselines and discussion

The project has no external, pre-existing system to benchmark against, so three internal baselines (ablations) were used to justify each guardrail rather than assuming it a priori:

vs. unguarded execution

Running the same generated snippet with a plain exec() and no validation silently returns whatever the code produced — including an empty DataFrame or a malformed output — with no indication that the result may be invalid. The validation layer converts such silent failures into explicit outcomes, and the correction layer automatically recovers a meaningful class of failures instead of exposing them to the user.

vs. rule-based-only routing

The default rule-based router is fully reproducible and needs no external API — but recognizes only phrasings covered by its predefined rules. The optional LLM-assisted fallback understands a wider range of formulations at the cost of external dependency and reduced determinism. That trade-off is why it is implemented as a fallback, never the default.

vs. the trusted registry path

The deterministic 12-question pipeline showed consistent, test-verified behavior throughout the evaluation. The optional Advanced mode trades some of that predictability for flexibility: it can answer questions outside the registry, but its AST allow-list rejects unsupported constructs and its output passes only a generic (not clinical) validator. This comparison supports keeping the registry path as the trusted default.

Overall, the evaluation supports the project's central claim: a small, fully specified set of clinical laboratory questions can be answered reliably through a generate → execute → validate → correct pipeline, while more open-ended LLM-generated analyses can be supported only when execution is sandboxed and every result is still verified by a deterministic validation stage before being presented to the user.

Conclusions

The project demonstrates that a small, fully specified set of clinical laboratory questions can be answered reliably and transparently by a generate → execute → validate → correct → present pipeline built on a single-source-of-truth question registry — and that the same pattern can be extended, cautiously, toward more open-ended LLM-authored queries as long as execution is sandboxed and every result still passes through a deterministic gate before it is trusted.

Advantages

  • Reliable and reproducible by default — the trusted path never calls an external model and is fully deterministic and test-covered.
  • Transparent and auditable — every run shows the generated code, the validation outcome, and the full correction history.
  • Maintainable — the config-driven registry keeps UI, generator, validator, and pipeline in sync; adding a question is a one-place change.
  • Safe-by-default extensibility — LLM-authored code is possible but strictly opt-in and sandboxed.
  • Usable for two audiences — the role-based Doctor / Researcher workspaces surface what each user needs without hiding the shared pipeline.

Limitations

  • Restricted, by design, to 12 predefined question types; arbitrary clinical questions require extending the registry or the weaker Advanced mode.
  • Operates on a single static CSV rather than a live SQL backend.
  • The rule-based corrector repairs only a small, explicit set of known typos — unlike a learned, fault-aware editor such as Self-Edit.
  • The sandbox's AST allow-list rejects some valid, more complex analyses along with unsafe ones.
  • Evaluation covers one dataset and one clinical domain; the experimental LLM mode was tested mostly with a mock LLM for control flow, not benchmarked at scale.

Future work

  • Broaden the question registry, or pair a more capable LLM-assisted router with the same validation guarantees, so more clinical questions can be answered through the trusted path.
  • Replace the static CSV with a live SQL backend so results reflect current data and larger cohorts can be queried efficiently.
  • Strengthen the guarded code-generation path: a broader, still-safe AST allow-list; benchmarking across multiple LLM providers; and a learned, fault-aware correction step in the spirit of Self-Edit.
  • Run a small user study with clinicians and researchers comparing the role-based workspace against ad-hoc querying.
  • Add authentication and multi-user session state if the system moves beyond a single-user course demo.
